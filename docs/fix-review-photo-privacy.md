# fix/review-photo-privacy — 후기 사진 비공개화와 메타데이터 제거

## 무엇을, 왜

개인정보처리방침 초안이 후기 사진에 대해 두 가지를 약속하는데 코드가 그 반대였다.

| 방침 문구 | #52 이후 실제 |
| --- | --- |
| "외부에서 임의로 접근할 수 없는 저장소에 보관하며, 본인에게만 짧은 시간 동안 유효한 열람 경로를 제공" | 버킷 정책이 `review-photos/*` 접두사를 **공개 읽기**로 열어둠. URL 이 한 번 새면 영구히 유효 |
| "저장 전에 촬영 위치(GPS 좌표)와 촬영 기기 정보 등 파일에 포함된 메타데이터를 모두 제거" | 제거 코드 없음. 업로드 바이트를 그대로 `putObject` |

방침을 사실에 맞춰 낮춰 쓰는 대신 코드를 방침에 맞추기로 했다(사용자 결정). 사진에는
집 주소가 그대로 찍힌 GPS 좌표가 들어오고, 후기는 "작성자 본인만 조회"가 설계 전제다.

## 핵심 설계 결정

1. **저장값을 공개 URL 이 아니라 버킷 키로 바꾼다.** 공개 URL 은 유출되면 회수할 방법이
   없다. DB 에는 `review-photos/{userId}/{uuid}.{ext}` 키만 남기고, 조회 시점에
   `ReviewPhotoService.presign` 이 **15분짜리 서명 URL** 로 바꿔 내보낸다.

2. **키에 업로더를 박는다.** `photoUrls` 는 클라이언트가 보낸 문자열을 그대로 저장하는
   필드다(#52 문서의 "업로드한 사람과 리뷰 작성자가 같은지 확인하지 않는다"). 서명은
   서버가 능동적으로 접근 권한을 발급하는 행위라, 남의 키를 넣어 보내면 이전보다 나빠진다.
   키 경로에 uploader 를 넣어두면 별도 테이블 없이 `키 접두사 == 소유자` 로 판정된다.
   소유자 키가 아니면 **서명하지 않고 원문 그대로** 통과시킨다(목 URL·옛 공개 URL 도 이 경로).

3. **메타데이터 제거는 디코드 후 재인코딩으로 한다.** EXIF 태그를 하나씩 지우는 방식은
   제조사 확장(MakerNote)·XMP·ICC 같은 걸 흘린다. 픽셀만 꺼내 다시 인코딩하면 파일에
   실린 것이 전부 떨어진다. jpg 는 품질 0.9 로 재인코딩한다 — 프론트가 이미 q80·1600px
   으로 줄여 보내므로 여기서 또 기본값(0.75)으로 깎으면 눈에 띄게 뭉갠다.

4. **jpg 로 내보낼 때 알파는 흰 배경에 눕힌다.** JPEG 인코더는 알파 채널을 받지 못하고
   `Bogus input colorspace` 로 죽는다(JDK 21 재현). content-type 을 jpeg 로 신고하고 실제로는
   투명 png 를 보내면 클라이언트 잘못이 500 으로 나가므로, 인코딩 전에 RGB 로 합성한다.

5. **webp·heic 를 화이트리스트에서 뺐다.** 3번이 ImageIO 재인코딩에 기대는데 ImageIO 는
   둘 다 읽지 못한다. "메타데이터가 남을 수 있는 형식을 받느니 안 받는다"를 택했다.
   프론트 픽커가 촬영·선택 원본을 **1600px·q80 JPEG 로 수렴**시켜 보내므로(iOS HEIC 포함,
   `NativeReviewPhotoPicker`) 실사용 경로에는 영향이 없다.

6. **프론트는 고치지 않아도 된다.** 업로드 응답 `{"url": ...}` 의 필드명을 유지했고,
   프론트는 그 값을 화면에 다시 쓰지 않는다 — 후기 사진 표시는 앱 문서 디렉터리의
   로컬 파일이 담당하고(`ReviewPhotoFileGateway`), 응답값은 `POST /reviews` 에 그대로
   넘기기만 한다. 그래서 반환값이 URL 에서 키로 바뀌어도 클라이언트 동작이 같다.

7. **소유자 판정에 현재 사용자를 다시 읽지 않는다.** `ReviewService` 의 조회는 전부
   `findBy...AndUserId` 라 리뷰의 `user_id` 가 곧 열람자다. 여기서 `getCurrentUser()` 를
   부르면 목록 조회에 리뷰 수만큼 조회가 붙는다.

## 스키마 / API 변경

**스키마 변경 없음.** `post_cook_reviews.photo_urls` 는 그대로 문자열 배열이고, 담기는
값의 형태만 공개 URL → 버킷 키로 바뀐다.

**API 계약 변경 없음** (필드명·응답 형태 동일). 의미만 바뀐다:

| 엔드포인트 | 이전 | 이후 |
| --- | --- | --- |
| `POST /reviews/photos` → `{url}` | 영구 공개 URL | 버킷 키(불투명 참조) |
| `GET /reviews/{id}`, `GET /recipes/{id}/reviews` → `photoUrls[]` | 저장값 그대로 | 15분 서명 URL |

허용 content-type 이 `jpeg/png/webp/heic` → `jpeg/png` 로 좁아졌다(위 결정 5).
디코딩되지 않는 파일은 415 가 아니라 **400** 이다(이미지인 척하는 파일 거부).

## 배포 시 함께 해야 하는 인프라 변경 (코드 아님)

**코드만 배포하면 사진이 비공개가 되지 않는다.** 아래 둘을 함께 해야 한다.

1. 버킷 `cookpilot-photos-167403240280` 의 **`review-photos/*` 공개 읽기 정책 제거**.
2. 인스턴스 역할 `cookpilot-ec2-ssm` 에 **`s3:GetObject`** 권한 확인 — 서명 URL 은 서명자의
   권한을 위임하므로, 역할에 읽기 권한이 없으면 서명 URL 이 403 을 돌려준다.

## 알려진 약점·후속

- **옛 리뷰의 사진은 깨진 채로 남는다.** 목 URL 이 저장된 행(#50 시절)과 공개 URL 이
  저장된 행(#52~현재)은 서명 대상이 아니라 원문 그대로 나간다. 공개 정책을 내리면 후자도
  404 가 된다. 베타 데이터라 정리 여부는 별도 판단.
- **EXIF orientation 도 함께 사라진다.** 회전 플래그에 의존하는 원본이라면 눕는다.
  프론트 픽커가 `maxWidth`/`imageQuality` 로 이미 재인코딩하며 회전을 굽는 경로라
  실사용에서는 문제 없을 것으로 보지만, 실기기 촬영으로 한 번 확인이 필요하다.
- **삭제 경로는 여전히 없다.** 리뷰가 append-only 라 사진 객체도 지우지 않는다. 방침
  제9조(계정 삭제 시 사진 파일까지 삭제)를 지키려면 별도 작업이 필요하다 — 이 브랜치 범위 밖.
- **고아 객체 정리 없음** (업로드 후 후기 미제출). #52 문서의 판단(S3 Lifecycle) 그대로 둔다.
- 로컬·CI 는 버킷 미설정이라 목 모드로 돌고 서명도 하지 않는다. 서명 URL 자체의 동작은
  AWS SDK 몫이라 테스트하지 않았고, 배포 후 실기기에서 확인해야 한다.

## 테스트

- `ReviewPhotoMetadataStripTest` (신규, 순수 단위) — EXIF APP1 세그먼트를 심은 JPEG 와
  tEXt 청크를 심은 PNG 를 만들어, 제거 후 해당 바이트열이 사라지고 이미지는 같은 크기로
  디코딩되는지 확인. 투명 png 를 jpeg 로 신고한 경우(위 결정 4)도 함께 확인.
- `ReviewPhotoUploadTest` — 업로드 픽스처를 진짜 이미지 바이트로 교체(재인코딩을 타므로
  `"fake-image-bytes"` 는 이제 400 이다). 저장 경로에 업로더가 박히는지, 이미지인 척하는
  파일이 400 인지 추가.
- Docker 가 없는 로컬에서는 Testcontainers 기반 `*ApiTest` 가 돌지 않는다 — CI 확인 필요.
