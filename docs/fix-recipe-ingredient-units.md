# 운영 레시피 재료 단위 백필

## 배경

앱에서 가자미쑥국을 열면 재료가 `가자미 50`, `물 200`처럼 단위 없는 숫자로만 보인다.
2026-08-17 운영 DB를 읽기 전용으로 감사한 결과 `recipe_ingredients.amount`는 있는데
`unit`이 `NULL`인 행이 **210건 / 26개 레시피**였다.

앞선 운영 레시피 카탈로그 정리(`fix/recipe-catalog-cleanup` 브랜치의
`docs/fix-recipe-catalog-cleanup.md`, 아직 미커밋)가 `양파(20g)`처럼 수량이 이름에 들어간
6,599건을 정규화했고, 이 210건은 그 뒤에 남은 잔여분이다. 앞의 정리로는 고칠 수 없었는데,
**괄호 안에 애초에 단위가 없었기 때문이다.**

## 원인은 임포터가 아니라 상류 데이터다

처음에는 임포터의 파싱 누락을 의심했다. 그래서 카탈로그 출처인 식품안전나라
조리식품의 레시피 DB(`COOKRCP01`) 원문 1,156건을 내려받아 26개 레시피를 대조했다.
결과는 반대였다 — 원문 `RCP_PARTS_DTLS` 자체에 단위가 없다.

```
가자미쑥국   가자미 50, 모시조개 15, 쑥 20, 물 200, 된장 9, 대파 4, 들깨가루 6
호두떡볶이   호두 15, 올리브유 4, 떡볶이 떡 80, 올리고당 20, 간장 1.5, 검정깨(볶은 것) 0.5
```

임포터는 있는 그대로 옮겼다. 그러므로 임포터를 고쳐 재임포트해도 이 210건은 그대로 남는다.
값을 직접 채우는 수밖에 없다.

## 단위를 `g`로 판정한 근거

원문에 단위가 없으니 추론이 필요하다. 세 가지가 서로 독립적으로 같은 답을 가리킨다.

**1. 같은 원문 안의 형제 재료가 `g`를 달고 있다.** 26개 중 6개가 여기에 해당해서 직접 증거가 된다.

| 레시피 | 원문 | 판정 |
| --- | --- | --- |
| 감자를 곁들인 야채스튜 | `양파 15, 청피망 15g, 가지 10g, 애호박 18g, …` | 양파만 단위 누락 → `g` |
| 풋마늘오징어김치 | `… 새우젓 0.75, 멸치액젓 0.2g, 설탕 1, 통깨 0.5` | 목록 전체가 `g` |
| 롤 삼계탕 | `마늘 15(3개)` — 다른 줄은 `마늘 10g(2개)` | 같은 재료의 같은 표기법 → `g` |
| 깻잎향을 입힌 관자 샐러드 | `돌나물(10g), … 올리브유(60g), 석류 원액(3g), 레시틴가루(0.5)` | `g` |
| 낙지 잣소스 냉채 | 전 재료 `g`, `배즙 37.5`만 누락 | `g` |
| 단호박 두부찜 | 전 재료 `g`, `식용유 0.7`만 누락 | `g` |

나머지 20개 레시피는 원문에 `g` 토큰이 아예 없어 근거 2·3에 의존한다.

**2. 출처 데이터셋의 표기 관례가 그램이다.** 원문 1,156건 전체의 단위 토큰 분포는
`g` 11,690 / `개` 495 / `장` 117 / `ml` 93 / `큰술` 47이다. 그램이 기본이고 나머지가 예외다.

**3. 값의 크기가 그램일 때만 성립한다.** `후추 0.01`, `흰후추 0.02`, `소금 0.38`,
`물 200~500`은 개·큰술·컵으로 읽으면 조리가 불가능하다. 1인분 열량과도 맞는다 —
가자미쑥국 123.4kcal(가자미 50g·된장 9g·들깨가루 6g 기준으로 계산한 값과 근사),
호두떡볶이 383.1kcal(호두 15g·떡 80g·올리고당 20g 기준).

210건 전수를 눈으로 확인했고, 개수·마리·장으로 읽는 것이 더 그럴듯한 행은 없었다.
각 행의 원문은 SQL의 레시피별 주석에 그대로 붙여 두어 나중에 재검증할 수 있게 했다.

## 적용 방법

SQL은 [2026-08-17-recipe-ingredient-units.sql](../infra/maintenance/2026-08-17-recipe-ingredient-units.sql)에 있다.
카탈로그 자체가 마이그레이션이 아니라 임포터로 운영 DB에 들어갔으므로, Flyway 마이그레이션이 아닌
`infra/maintenance/` 일회성 스크립트 관례를 따랐다.

한 트랜잭션 안에서 실행하며, 감사 시점과 데이터가 다르면 **UPDATE 전에** 실패한다.

| 전제조건 | 실패 조건 |
| --- | --- |
| 백필 목록 크기 | 210행이 아님 |
| 운영 스냅샷 | `recipes` 수가 1,150이 아님 |
| 대상 존재 | 210개 UUID 중 사라진 행이 있음 |
| 수량 일치 | `amount`가 감사 시점과 다름(단위 판정 근거가 흔들림) |
| 미적용 상태 | 이미 `unit`이 채워진 행이 섞여 있음(덮어쓰지 않는다) |
| 잔여 결손 | 목록 밖에 같은 결손이 새로 생김(재감사 필요) |

마지막에 `unit IS NULL AND amount IS NOT NULL`이 0행인지 확인하고 커밋한다.

## 안전 조치

적용 직전 전체 덤프를 회전에서 빠지는 위치에 별도 보관했다.

`s3://cookpilot-backup-167403240280/manual/cookpilot-pre-unit-backfill-20260817T094249Z.sql.gz`

**자동 백업(`db/`)만 믿으면 안 되는 상황이었다.** 적용 시점에 `db/`의 최신 덤프는
`20260816-190001`이고, `manual/`의 `pre-recipe-cleanup`도 이름 그대로 카탈로그 정리 **이전**
상태였다. 즉 레시피 1,150건인 현재 상태를 담은 덤프가 하나도 없어서, 롤백하면 카탈로그 정리까지
되돌아갈 판이었다. 그래서 새로 떴다.

덤프는 받아서 검증했다 — `gzip -t` 통과, `PostgreSQL database dump complete` 표식 존재,
테이블 12개, `recipes` 1,150행 / `recipe_ingredients` 13,064행으로 라이브와 일치.

## 검증

먼저 운영 DB에서 읽어온 1,150개 레시피 / 13,064개 재료 행을 로컬 PostgreSQL 17.6에 그대로
재현해 전제조건과 결과를 확인했다.

- 정상 경로: `UPDATE 210` → 잔여 결손 0행, `unit='g'` 11,281 → 11,491행
- 재실행: `210행에 이미 unit 이 채워져 있다`로 중단
- `amount` 변경: `1행의 amount 가 감사 시점과 다르다`로 중단
- 대상 행 삭제: `백필 대상 1행이 recipe_ingredients 에 없다`로 중단
- 목록 밖 결손 주입: `백필 목록 밖에 unit 결손이 11281행 더 있다`로 중단
- 실패한 경우 데이터는 변경되지 않음(트랜잭션 롤백)

## 실행 결과

2026-08-17, `aws ssm send-command`로 운영 서버(`i-0068e3a496881f57e`)의 `cookpilot-db-1`
컨테이너에 적용했다. 앞선 카탈로그 정리와 같이 **같은 운영 DB에서 먼저 전체 트랜잭션을
`ROLLBACK`으로 리허설**한 뒤 동일한 SQL을 `COMMIT`했다.

- 리허설: 전제조건 6종 통과, `UPDATE 210`, `ROLLBACK` 후 결손 210건 그대로 → 무변경 확인
- 적용: `UPDATE 210`, `COMMIT`
- 적용 후 `unit IS NULL AND amount IS NOT NULL` = **0행**
- `unit='g'`: 11,281 → **11,491행**(+210)
- 레시피 1,150건 / 재료 13,064행 — 변동 없음
- 앱 헬스체크 `UP`

**전수 회귀 검사.** 적용 전후로 1,150개 레시피 상세를 모두 API로 받아 재료의
`name`/`amount`/`unit`/`required`와 레시피의 `title`/`description`/`baseServings`/`imageUrl`을
대조했다. 차이는 **정확히 210건이고 전부 `unit: null → g`**였다. 그 외 필드 변경, 재료 행
추가·삭제, 레시피 증감은 0건이다. 기존에 단위가 있던 행은 하나도 건드려지지 않았다.

```
가자미쑥국  가자미 50g · 모시조개 15g · 쑥 20g · 물 200g · 된장 9g · 대파 4g · 들깨가루 6g
```

## 함께 발견한 것 — 이번 범위 아님

같은 감사에서 **재료 이름 오염 570건 / 359개 레시피**를 확인했다. 단위 문제와 원인이 다르고
규모도 훨씬 커서 이번 스크립트에 넣지 않았다.

임포터가 원문을 쉼표로만 쪼개서, 그룹 머리말과 괄호 안 하위 재료가 이름에 섞여 들어갔다.

```
'올리브유 5 양념장: 간장'  = 4      -- 재료 두 개가 한 행에 뭉쳤다(올리브유 5g이 사라짐)
'비빔밥: 쌀밥'            = 210    -- 그룹 머리말이 이름에 붙었다
'다시마 국물 200(물'      = 300    -- 괄호 안 하위 재료가 쉼표에서 끊겼다
'1인분 기준<br>'          = NULL   -- HTML 조각이 재료로 적재됐다
'200g)'                  = NULL   -- 이름과 수량이 다른 행으로 찢어졌다
```

이 중 18건은 이번 백필 대상과 겹치지만, 겹치는 행도 `amount` 값 자체는 그램이 맞아
단위를 붙이는 것은 옳다. 이름 교정은 별도 작업으로 남긴다.

`amount`와 `unit`이 모두 비어 있는 353건도 남아 있다. 83건은 `약간`·`적당량`류로 의도된
공백이지만(앞선 정리의 정책), 270건은 위 이름 오염과 같은 뿌리다.
