# 워크로그 — 운영 레시피 데이터 복구 (2026-08-17)

가자미쑥국 재료가 `가자미 50`처럼 단위 없이 보인다는 제보에서 시작해, 같은 뿌리의 결함
세 개를 연달아 고쳤다. 단위 결손 → 이름 오염 → 그룹 소실 순이다.

| | 대상 | 결과 |
| --- | --- | --- |
| 단위 결손 백필 | 210행 / 26개 레시피 | 결손 0행, `unit='g'` 11,281→11,491 |
| 이름 오염 복구 | 305개 레시피 재구성 | 오염 770→267행, 재료 13,064→13,056 |
| 그룹 복원 | 952개 레시피 | 2,957행 / 163종 |

상세는 [단위](fix-recipe-ingredient-units.md) · [이름](fix-recipe-ingredient-names.md) ·
[그룹](feat-recipe-ingredient-group.md) 문서에 있다. 이 문서는 **왜 그렇게 했는지**만 남긴다.

## 결정 기록

### 1. 원인 — 임포터 버그가 아니라 상류 데이터 결손

**상황.** 단위가 없으니 임포터가 파싱에서 흘렸다고 봤다.

**검토한 대안.**
- (A) 임포터를 고쳐 재임포트한다
- (B) 값을 직접 채운다

**측정.** 출처인 식품안전나라 `COOKRCP01` 원문 1,156건을 내려받아 26개 레시피를 대조했다.
원문 `RCP_PARTS_DTLS` 자체에 단위가 없었다 —
`가자미쑥국: "가자미 50, 모시조개 15, 쑥 20, 물 200, 된장 9, 대파 4, 들깨가루 6"`.

**선택: (B).** **(A) 기각 이유 — 재임포트해도 같은 결손이 그대로 돌아온다.**
이건 예상과 정반대의 결과였고, 이후 판단의 전제를 바꿨다.

> 원본 API는 sample 키로도 접근된다. 단 구간 폭이 정확히 1000이어야 응답한다
> (`1/1000`, `1001/2000` → 1,156건 전량). `1/100`이나 `101/200`은 5건만 준다.

### 2. 단위를 `g`로 판정한 근거

**검토한 대안.** (A) NULL로 두고 UI에서 처리 (B) 재료별로 추정 (C) 일괄 `g`

**근거 셋이 독립적으로 같은 답을 가리켰다.**
1. 26개 중 6개는 **같은 원문의 형제 재료가 `g`를 달고 있다** — `양파 15, 청피망 15g, 가지 10g`,
   `새우젓 0.75, 멸치액젓 0.2g`, `마늘 15(3개)` vs 다른 줄 `마늘 10g(2개)`. 직접 증거다.
2. 출처 전체 단위 토큰 분포 `g` 11,690 / `개` 495 / `장` 117 / `ml` 93 — 그램이 표기 관례.
3. 값의 크기가 그램일 때만 성립한다(`후추 0.01`, `소금 0.38`, `물 200~500`).
   1인분 열량과도 맞는다(가자미쑥국 123.4kcal, 호두떡볶이 383.1kcal).

**선택: (C).** 210행 전수를 눈으로 확인했고 개·마리·장으로 읽는 게 나은 행은 없었다.
**(A) 기각 — 사용자가 보는 화면의 문제를 UI로 미루는 것일 뿐.**
**(B) 기각 — 근거 1·2가 일괄 g를 지지하는데 행마다 다르게 추정하면 재현·검증이 불가능하다.**

### 3. Flyway 마이그레이션이 아니라 `infra/maintenance/` 일회성 스크립트

카탈로그 1,150건 자체가 마이그레이션이 아니라 **임포터로 운영 DB에 직접 들어갔다.**
그래서 마이그레이션에 넣으면 새 환경에서는 대상 행이 없어 아무 일도 하지 않는다.
앞선 `2026-08-17-recipe-catalog-cleanup.sql`의 관례를 따랐다.

예외는 그룹 컬럼(→ 6번). 그건 **스키마** 변경이라 모든 환경에 필요해서 `V15`로 넣었다.

### 4. 운영 접근 경로 — 브라우저 콘솔이 아니라 AWS CLI + SSM

**상황.** 이 맥에 AWS CLI도 자격증명도 없었다. "코덱스는 브라우저로 콘솔을 조작하던데"라는
지적을 받고 실제 가능 여부를 확인했다.

**검토한 대안.** (A) 브라우저로 AWS 콘솔 (B) CLI + SSM

**확인한 사실.** 브라우저 자동화 도구는 있다(`/connect-chrome`, `/browse`). 막힌 건 브라우저가
아니라 로그인이었다. 그리고 **콘솔에서는 이 DB에 질의할 방법이 아예 없다** — RDS가 아니라
EC2 안 Docker Postgres이고 5432가 닫혀 있어서, 콘솔 경로도 결국
`Session Manager → 브라우저 터미널 → docker exec psql`이다.

**선택: (B).** **(A) 기각 이유 — 352줄 SQL을 브라우저 터미널에 붙여넣는 건 붙여넣기 길이
제한과 에러 출력 유실로 실제로 잘 깨진다.** CLI는 stdout과 종료코드를 그대로 받는다.
CI의 배포 경로와도 같다.

관리자 권한 없이 설치했다. `installer -pkg`는 `/usr/local`을 요구해 실패해서
`pkgutil --expand-full`로 페이로드만 `~/.local`에 풀었다.

### 5. 적용 직전 백업을 새로 뜬 이유

**예상과 달랐던 지점.** 백업이 있으니 괜찮다고 생각했는데, 확인해보니 **현재 상태를 담은
복원 지점이 하나도 없었다.** 자동 백업 최신은 `20260816-190001`, 수동 백업은
`pre-recipe-cleanup` — 둘 다 카탈로그 정리 **이전**(레시피 1,164건)이었다.
그대로 갔으면 롤백 시 정리 작업까지 되돌아갔을 것이다.

그래서 매 단계마다 `manual/`에 새로 떴다(`db/`는 14개 초과분을 자동 삭제하므로 회전에서
빠지는 곳에 둔다). 덤프는 `gzip -t` + 완료 표식 + 행 수까지 검증하고 진행했다.

절차는 3회 모두 동일하다: **백업 → 리허설(`ROLLBACK`) → 적용(`COMMIT`) → 전수 회귀 대조.**

### 6. 이름 오염 — 표면 수정이 아니라 원문 재파싱

**상황.** `'올리브유 5 양념장: 간장' = 4`처럼 재료 두 개가 한 행에 뭉치고 올리브유 5g이
아예 사라진 행이 있었다. 이름만 고쳐서는 소실된 재료가 돌아오지 않는다.

**검토한 대안.** (A) 이름만 정규식으로 정리 (B) 원문을 다시 파싱해 재구성

**선택: (B).** **(A) 기각 — 소실된 재료를 되살릴 수 없다.**

### 7. `UPDATE`가 아니라 `DELETE` + `INSERT`, 그리고 그게 안전한 조건

기존 재료 `id`가 UUIDv5인데 **네임스페이스를 알 수 없다**(임포터가 repo에 없다).
후보 조합을 여러 개 시도했지만 재현하지 못했다. 그래서 소실 재료를 넣으려면 새 id가 필요하고,
행 정렬이 어긋나므로 대상 레시피의 행을 지우고 다시 넣는 쪽이 깨끗하다.

**여기서 위험한 제약을 발견했다.** `personal_ingredient_adjustments.original_ingredient_id`가
`recipe_ingredients(id)`를 **`ON DELETE CASCADE`**로 참조한다 — 재료 행을 지우면 사용자의
개인 레시피 수정이 조용히 함께 삭제된다.

운영을 확인하니 그 테이블 0행, `recommendation_feedback`의 재료 참조 0건, 리뷰 0건이었다.
**지금은 잃을 게 없지만 실사용자가 개인화를 시작하면 닫히는 창이다.** 그래서 스크립트
전제조건에 이 검사를 넣어, 참조가 하나라도 있으면 실행을 거부하고 "UPDATE 방식으로 다시
설계할 것"이라는 메시지를 내도록 했다.

재구성 행의 id는 결정론적으로 만들었다 —
`uuid5(uuid5(URL,'https://cookpilot.app/recipe-ingredient'), '<recipe_id>:<sort_order>:<name>')`.
나중에 그룹을 매칭할 때 이 결정이 그대로 값을 했다(→ 8번).

### 8. 파서 — 커버리지보다 신뢰도

원문에 일관된 문법이 없다. 그룹 머리말만 6가지 형태(`- 주재료 :`, `●`, `[주재료]`,
`갈치구이 :`, 콜론 없는 `재료`, `(반죽재료)`)로 섞이고 문장 중간에도 나오며,
원문 자체에 괄호 짝이 안 맞는 오타(`바지락(모시조개( 200g(30개)`)까지 있다.

**선택: 확실하게 읽히는 것만 통과시키고, 애매한 항목이 하나라도 있는 레시피는 전체를
대상에서 제외한다.** 최대 커버리지를 노리지 않았다.

**측정 조건과 결과.** 원문과 제목이 매칭되는 1,140개 레시피 기준, 파서 개선을 거치며
74% → 81% → 90%(1,027개)가 전부 확실하게 읽혔다. 실제 수정 대상은 오염이 있으면서
확신이 서는 305개로 좁혔고, 오염 503/770행을 해소했다. 남은 267행은 원문이 애매한 것들이다
(`고구마 3~4개`, `각 15g씩`, `1캔=130g`, 원문 괄호 오타).

**개발 중 잡은 파서 버그 두 개.** 둘 다 조용히 데이터를 망가뜨리는 종류라 기록해 둔다.
1. **괄호 안 수량 선택** — `저염베이컨(46g, 3장)`에서 마지막 조각 `3장`을 수량으로 잡았다.
   주 수량은 `46g`이다. 질량·부피(g/ml/kg/L)를 우선하도록 고쳤고, 그게 없을 때만 마지막
   조각을 쓴다(`다시마(5x5cm, 2장)` → 2장).
2. **콜론 없는 머리말 위치** — 공백 뒤 그룹 낱말을 전부 머리말로 인정했더니
   `멸치 국물 100g`이 `멸치`(수량 없음) + 고아 `100g`으로 쪼개졌다. `다시마 국물`,
   `닭 육수`처럼 재료명 끝에 그룹 낱말이 들어간 경우를 오인한 것이다. 인정 위치를
   세그먼트 맨 앞과 닫는 괄호 뒤로 제한했다.

   → **원칙: 못 고치고 남기는 편이 수량을 깨뜨리는 것보다 낫다.** 이 결정으로
   `돼지고기 밑간 간장` 같은 이름이 일부 남았지만 수량은 안전하다.

**검증에서 확인한 것.** 그램 총량 감소가 딱 1건(`키조개샤브샤브` 481.5→380.5g)이었는데,
확인해보니 **현재 데이터가 `다시마 국물 200`과 그 재료 `물 300+다시마 1+대파 5`를 이중
계산**하고 있었다. 괄호 안은 국물 만드는 법이므로 줄어드는 게 맞다. 감소는 결함 신호일
거라 보고 전수 확인했는데 반대였다.

### 9. 오염 규모 정정 — 570행/359레시피 → 770행/444레시피

처음 보고한 숫자가 **과소집계**였다. 오염 탐지에 콜론 없는 머리말(`재료 바나나`)을
넣지 않아서다. 파서를 만들며 탐지기를 강화한 뒤 실제 규모가 드러났다.

### 10. 그룹 — 이름 접두어가 아니라 컬럼 추가

**상황.** 파서가 그룹을 정확히 뽑아내는데 담을 컬럼이 없어 이름 복구 때 버렸다.
사용자가 "나중에 분류할 때 필요하다"고 해서 되살렸다.

**검토한 대안.**
- (A) 이름에 접두어로 붙인다
- (B) 버린 채로 두고 필요할 때 다시 파싱한다
- (C) `ingredient_group` 컬럼을 추가한다

**선택: (C).** **(A) 기각 — 바로 그게 이름 오염의 원인이었다.**
**(B) 기각 — 원문 재파싱은 언제든 되지만, 파싱 결과를 현재 행에 매칭하는 비용이 매번 든다.**

**매칭은 추측하지 않는 두 경로만 썼다.** (A) 재구성한 305개는 id가 결정론적이라 다시
계산했고, 계산한 2,957개가 운영에 **하나도 빠짐없이 존재**해서 7번의 id 규칙이 실제로
재현된다는 것까지 검증됐다. (B) 그 밖은 파싱 결과가 현재 행과 `(이름, 수량, 단위)` 순서까지
완전히 일치할 때만. 결과 952개 레시피 / 2,957행. 나머지 198개는 `NULL`로 남겼다.

**`ADD COLUMN IF NOT EXISTS`를 쓴 이유.** 백필이 배포(=main 머지)를 기다릴 수 없어서 운영에는
유지보수 스크립트로 컬럼을 먼저 넣었다. 그래서 배포 시 `V15`는 운영에서 무해하게 지나가고
새 환경에서는 컬럼을 만든다. 두 경로 모두 로컬에서 검증했다.

### 11. 그룹 값을 정규화하지 않은 이유

163종에 `주재료`/`재료`, `필수 재료`/`필수재료` 같은 표기 차이와 `고추장소스`,
`저나트륨된장소스`처럼 레시피별 고유명이 섞여 있다.

**선택: 원문 그대로 저장.** 분류 체계는 사용자가 정할 몫이고, **정규화는 나중에 언제든
할 수 있지만 합쳐버린 값은 되돌릴 수 없다.** 정규화 후보를 보라고 전체 목록을
`infra/maintenance/tools/ingredient-group-values.txt`에 남겼다.

### 12. 샌드박스 임대 리스크 — 확인했으나 보류(사용자 결정)

권한 세트 이름 `myisb_IsbUsersPS`가 걸려 확인했더니, IAM 역할
`InnovationSandbox-myisb-SandboxAccountRole`이 있고 그 역할 조회를 관리 계정
(`403164878212`)의 SCP가 명시적으로 거부한다. **AWS Innovation Sandbox 임대 계정이 맞다.**

ISB는 임대 기간·예산을 넘기면 계정 리소스를 정리하고 계정을 재사용 풀로 반납한다.
문제는 **백업 버킷이 같은 계정에 있다**는 것 — `infra/README.md`의 재해 복구 절차
("새 EC2 만들고 S3 백업에서 복원")가 이 시나리오를 못 막는다. 임포터도 repo에 없어
운영 DB가 유일본이다.

사용자가 "아직 걱정할 레벨은 아니다"라고 판단해 대응은 하지 않았다. 임대 만료 시점이
심사·데모 일정을 넘기는지 확인이 필요하다는 것만 남긴다.

## 남은 것

- 이름 오염 잔여 **267행 / 139개 레시피** — 원문이 애매해 사람 판단이 필요하다.
  이유까지 `infra/maintenance/tools/deferred-recipes.json`에 남겼다.
- 그룹이 비어 있는 **198개 레시피** — 113개는 원문 애매, 72개는 정렬 불일치.
- **그룹 API·프론트 노출** — 엔티티 필드 + DTO 작업이 있어야 조리 화면에서 묶인다.
  지금은 DB에만 있고 API 응답은 적용 전후 완전히 동일하다.
