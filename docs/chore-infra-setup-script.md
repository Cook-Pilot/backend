# chore/infra-setup-script — 운영 서버 구성을 코드로

## 무엇을, 왜

운영 서버(AWS EC2)를 세팅하면서 손으로 넣은 설정들이 **그 서버 안에만 존재했다.** nginx 프록시, rate limit, 도커 로그 로테이션, 스왑, 백업 cron — 서버가 날아가면 대화 기록을 뒤져가며 복구해야 하는 상태였다. 이걸 `infra/` 로 옮겨 **재현 가능한 자산**으로 만든다.

문서 역할도 겸한다. 지금까지 "서버가 어떻게 구성돼 있는지"는 아무 데도 적혀 있지 않았다.

## 핵심 설계 결정

1. **서버의 실제 파일을 그대로 가져왔다.** 이상적인 설정을 새로 쓴 게 아니라 지금 도는 서버에서 복사했다 — 문서와 실제가 어긋나는 걸 막는다.
2. **`setup.sh` 는 멱등.** 여러 번 실행해도 안전하다(설치 여부·스왑 존재·cron 중복을 확인). 새 서버 구축과 기존 서버 재적용에 같은 스크립트를 쓴다.
3. **비밀은 스크립트가 만들지 않는다.** `.env` 생성은 사람이 한다. 스크립트는 무엇을 채워야 하는지 안내만 하고 끝낸다.
4. **컨테이너 기동도 자동으로 하지 않는다.** 설정을 확인한 뒤 사람이 올린다 — 복구 상황에서 DB 복원 순서가 앞설 수 있어서다.
5. **자격증명은 어디에도 넣지 않는다.** AWS CLI 를 설치하되 `aws configure` 를 하지 않는다. EC2 인스턴스 역할이 주입한다.

## 포함된 것

| 파일 | 내용 |
| --- | --- |
| `infra/setup.sh` | Docker·nginx·AWS CLI 설치, 로그 로테이션, 스왑 2GB, 백업 cron 등록 |
| `infra/README.md` | 운영 환경 요약, 새 서버 구축, **재해 복구 절차**, 운영 메모 |
| `infra/backup.sh` | DB 백업(pg_dump → gzip → S3, 최근 14개 유지) |
| `infra/nginx/cookpilot.conf` | 80 → 8080 리버스 프록시 |
| `infra/nginx/ratelimit.conf` | 업로드 10r/m, 익명발급 3r/m, 429 응답 |
| `infra/docker/daemon.json` | 컨테이너 로그 10MB × 3 |
| `infra/docker-compose.override.yml` | watchtower 임시 조치(`DOCKER_API_VERSION`) |

## 알려진 약점·후속

- **복구 리허설을 아직 안 했다.** 절차를 적어두기만 한 상태라, 실제로 새 인스턴스에서 한 번 돌려봐야 신뢰할 수 있다.
- **`docker-compose.prod.yml` 은 여전히 수동 배포다.** Watchtower 가 이미지만 교체하기 때문인데, SSM 배포로 전환하면 해소된다(후속 작업).
- **watchtower 자체가 아카이브된 프로젝트다**(2025-12-17). override 는 임시 조치이며 대체가 예정돼 있다.
- EBS 스냅샷은 설정하지 않았다 — DB 는 S3 백업, 서버 설정은 이 디렉터리로 재현 가능하다는 판단.
