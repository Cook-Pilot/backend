# 카탈로그 검색

## 무엇을 하나

- `GET /api/v1/recipes/search`에서 요리명과 재료명으로 활성 레시피를 검색한다.
- 응답은 페이지 단위이며 기존 목록과 같은 요약 필드, 현재 사용자의 즐겨찾기·개인 버전 상태를 포함한다.

## 설계 결정

- 기존 `GET /recipes`의 배열 응답은 앱 호환성을 위해 유지한다.
- 검색 조건은 요리명과 재료명을 함께 주면 AND로 결합한다.
- 재료 검색은 `recipe_ingredients` 를 `EXISTS` 서브쿼리로 훑는다. 목록 응답에 재료가 없어
  클라이언트가 거를 수 없기 때문에 서버에서 판단해야 한다.
- 검색어의 LIKE 메타문자(`%`, `_`, `\`)는 이스케이프한다. 그대로 넘기면 사용자가 친 `%`가
  와일드카드로 동작한다.
- 페이지는 1부터 시작하고 크기는 서버에서 1~50으로 제한한다. 요청 페이지가 마지막을 넘으면
  마지막 페이지를 돌려준다.
- 제목만 같은 별개 조리법이 있으므로 제목 유니크 제약이나 일괄 삭제는 사용하지 않는다.

## 데이터 출처

- 원본은 공공데이터포털의 [식품의약품안전처 조리식품 레시피 DB(COOKRCP01)](https://www.data.go.kr/data/15060073/openapi.do)다.
- 공공데이터포털 표기 기준 비용은 무료이고 이용허락범위 제한이 없다.

## API

`GET /api/v1/recipes/search?title=파스타&ingredient=토마토&page=1&size=9`

응답 필드: `items`, `page`, `pageSize`, `totalPages`, `totalItems`.

## 카탈로그 데이터 품질은 이 PR에서 다루지 않는다

재료 수량 표기(`가지(90g)`)를 구조화하는 Flyway 마이그레이션이 처음에는 함께 있었으나
리뷰(#60)에서 걷어냈다. **RDS로 넘기면서 DB를 밀고 파싱이 제대로 된 버전으로 다시 적재할
계획이라, 지금 데이터를 고치는 마이그레이션은 그때 무의미해진다.** 대표 이미지 교체도 같은
이유로 마이그레이션이 아니라 운영 DB에 직접 반영한다.

남은 전제와 후속:

- 운영 대량 데이터를 만든 importer가 저장소에 없어 현재 적재는 재현할 수 없다.
  재적재 계획은 이 importer(또는 그 대체물)를 먼저 확보해야 성립한다.
- 출발점은 `fix/recipe-ingredient-units` 의 `infra/maintenance/tools/` 에 있는 파서들이다.
  2026-08-17 운영 데이터 복구가 이 도구들로 이뤄졌다.
- 분수·범위·묶음 수량은 숫자형 `amount` 만으로 보존할 수 없다. 재적재 시 스키마 차원의
  결정이 필요하다.
