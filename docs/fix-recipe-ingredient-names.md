# 운영 레시피 재료 이름 오염 복구

## 배경

[재료 단위 백필](fix-recipe-ingredient-units.md)을 하면서 원인이 다른 결함을 함께 발견했다.
재료 이름에 그룹 머리말과 괄호 안 하위 재료가 섞여 들어가고, **그 과정에서 재료 자체가
소실된 행**이 있다.

```
'올리브유 5 양념장: 간장'   = 4      재료 두 개가 한 행에 뭉치고 올리브유 5g 이 사라졌다
'재료 검은깨'              = 8      콜론 없는 그룹 머리말이 이름에 붙었다
'방울토마토(20g) 소스 통계피' = 20     닫는 괄호 뒤 머리말을 못 끊어 통계피가 사라졌다
'채소국물 8컵(표고버섯'      = NULL   괄호 안 하위 재료가 쉼표에서 절단됐다
'1인분 기준<br>'           = NULL   HTML 조각이 재료로 적재됐다
```

원인은 임포터가 원문 `RCP_PARTS_DTLS`를 **쉼표로만 쪼갠 것**이다. 원문에는 줄바꿈으로 나뉜
그룹, `주재료:`/`[양념]`/`● 국물 :`/콜론 없는 `재료` 등 6가지 머리말 형태, 괄호 안 하위 재료
목록, `<br>` 태그가 섞여 있다.

운영 스냅샷 기준 오염 **770행 / 444개 레시피**.

> 단위 백필 때 "570행 / 359개 레시피"로 보고했는데 과소집계였다. 콜론 없는 머리말
> (`재료 바나나`)을 탐지에 넣지 않아서다. 실제 규모는 770행 / 444개 레시피다.

## 왜 이름만 고칠 수 없나

소실된 재료를 되살리려면 `INSERT`가 필요하고, 기존 재료 `id` 생성 규칙(UUIDv5, 네임스페이스
불명 — 임포터가 repo에 없다)을 재현할 수 없다. 그래서 **대상 레시피의 재료 행을 지우고
원문을 다시 파싱한 결과로 넣는다.**

### 이 방식이 안전한 이유, 그리고 안전하지 않게 되는 조건

`personal_ingredient_adjustments.original_ingredient_id`는 `recipe_ingredients(id)`를
**`ON DELETE CASCADE`**로 참조한다. 재료 행을 지우면 사용자의 개인 레시피 수정이 조용히
함께 삭제된다. 적용 시점에 그 테이블은 0행이었고 `recommendation_feedback`의 재료 참조도
0건이어서 잃을 것이 없었다.

**사용자가 개인화를 시작한 뒤에는 이 스크립트를 그대로 쓰면 안 된다.** 전제조건이 그 조건을
검사해서 참조가 하나라도 있으면 실행을 거부한다. 그때는 `UPDATE` 기반으로 다시 설계해야 한다.

## 파서

`infra/maintenance/tools/parse_recipe_parts.py`. 원문에 일관된 문법이 없으므로 **확실하게
읽히는 것만 통과시키고 애매한 것은 전부 보류**한다. 애매한 항목이 하나라도 있는 레시피는
레시피 전체를 대상에서 제외한다.

처리하는 것:

- 그룹 머리말 — `- 주재료 :`, `●두유 드레싱 :`, `[주재료]`, `(반죽재료)`, `갈치구이 :`,
  콜론 없는 `재료`/`소스`/`양념`. 문장 중간에 나오는 것도 끊는다.
- 괄호 안 쉼표를 보존한 항목 분리 — `다시마(5x5cm, 2장)`이 두 재료로 쪼개지지 않는다.
- 수량 — `50g`, `(20g)`, `75g(3/4모)`, `1/2개`, `⅔컵`, `0.5Ts`→큰술, `5㎖`→ml, `우유20g`
- 단위 없는 맨 숫자는 `g`로 읽는다([단위 백필](fix-recipe-ingredient-units.md)의 근거와 동일)
- `적당량`/`약간`은 수량을 비우고 단위에 남긴다

보류하는 것: `고구마 3~4개`(범위), `각 15g씩`, `1캔=130g`, `물녹말(녹말가루 10g, 물 10g)`
(괄호 안이 재료 목록), `후춧가루(0.5g`(원문 괄호 오타).

### 개발 중 잡은 파서 버그 두 개

기록해 두는 이유는, 둘 다 조용히 데이터를 망가뜨리는 종류였기 때문이다.

1. **괄호 안 수량 선택** — `저염베이컨(46g, 3장)`에서 마지막 조각(`3장`)을 수량으로 잡았다.
   주 수량은 `46g`이고 `3장`은 대체 계량이다. 질량·부피 단위(g/ml/kg/L)를 우선하도록 고쳤다.
   `다시마(5x5cm, 2장)`처럼 질량·부피가 없을 때만 마지막 조각을 쓴다.
2. **콜론 없는 머리말 위치** — 공백 뒤 그룹 낱말을 전부 머리말로 인정했더니
   `멸치 국물 100g`이 `멸치`(수량 없음) + 고아 `100g`으로 쪼개졌다. 재료명 끝에 그룹 낱말이
   들어간 경우(`다시마 국물`, `닭 육수`)를 오인한 것이다. 인정 위치를 세그먼트 맨 앞과
   닫는 괄호 뒤로 제한했다. **못 고치고 남기는 편이 수량을 깨뜨리는 것보다 낫다.**

## 검증

운영에서 읽어온 1,150개 레시피 / 13,064개 재료 행을 로컬 PostgreSQL 17.6에 재현하고,
`ON DELETE CASCADE` FK까지 만들어 확인했다.

적용 전 정적 검증:

- 그램 총량: 증가 139 · 동일 165 · **감소 1**
  감소한 `키조개샤브샤브`(481.5→380.5g)는 올바른 수정이다. 현재 데이터가
  `다시마 국물 200`과 그 재료인 `물 300 + 다시마 1 + 대파 5`를 이중 계산하고 있었다.
  괄호 안은 국물 만드는 법이므로 `다시마 국물 200g`만 남는 것이 맞다.
- 오염 아닌 재료가 사라지는 건: 6건. 전부 검토했고 모두 정상이다
  (`베이컨밀푀유`의 `채소국물 8컵(표고버섯, 다시마, 무, 마늘, 대파뿌리, 양파)` —
  괄호 안은 수량 없는 육수 구성이라 `채소국물 8컵`으로 합쳐지는 것이 맞다).
- 가드: 재실행 / 개인화 데이터 참조 / 재료 행수 불일치 각각 의도한 메시지로 중단,
  실패 시 데이터 무변경.

## 실행 결과

2026-08-17, SSM으로 운영 서버(`i-0068e3a496881f57e`)에 적용했다. 리허설(`ROLLBACK`) 후
동일 SQL을 `COMMIT`했다.

- 리허설: 전제조건 통과, `DELETE 3890` / `INSERT 3882`, 롤백 후 13,064행 그대로
- 적용: `DELETE 3890` / `INSERT 3882`, `COMMIT`
- 오염 행 **770 → 267**
- 재료 행 13,064 → 13,056 (머리말 단독 행 제거와 소실 재료 복구의 합)
- 레시피 1,150건 변동 없음 · 단위 결손 0행 유지 · 앱 헬스 `UP`

**전수 회귀 검사.** 적용 전후 1,150개 레시피 상세를 API로 받아 대조했다.
재료가 바뀐 레시피는 **정확히 대상 305개뿐이고 대상 밖 변경은 0건**이다.
레시피의 `title`/`description`/`baseServings`/`imageUrl` 변경도 0건이다.

```
갈치고추장구이  전: '갈치구이 : 갈치'=50g | '현미유 4g 고추장양념 : 고추장'=5g | 양파=5g …
              후: 갈치=50g | 현미유=4g | 고추장=5g | 양파=5g …      ← 현미유 4g 복구
```

## 남은 것

- **보류 139개 레시피(오염 267행).** 원문 자체가 애매해서 사람이 판단해야 한다.
- **그룹 정보를 버렸다.** 파서는 `양념장`/`소스`/`국물` 그룹을 뽑아내지만
  `recipe_ingredients`에 담을 컬럼이 없어 저장하지 못했다. 컬럼 추가는 프론트 표시까지
  얽히므로 별도 작업으로 남긴다. 지금은 `감자냉채`처럼 `단촛물`과 `겨자초장`의 `소금`이
  구분 없이 나란히 보인다(오염 상태에서도 마찬가지였으므로 회귀는 아니다).
- **임포터가 repo에 없다.** 카탈로그를 다시 만들 수 없어 운영 DB가 유일본이다.
  이번에 만든 파서가 그 임포터를 다시 쓸 때의 출발점이 된다.
