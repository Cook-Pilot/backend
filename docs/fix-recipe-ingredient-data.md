## 무엇을 왜

레시피 카탈로그의 재료 데이터가 세 방향으로 망가져 있었다. 원인은 임포터 버그 하나가 아니라
**상류 원문(식품안전나라 `COOKRCP01`)의 결손 + 임포터가 그 결손을 다루지 못한 것**이 겹친 결과다.

| 작업 | 증상 | 결과 |
| --- | --- | --- |
| 단위 결손 백필 | `amount`는 있는데 단위가 비어 조리 화면에 숫자만 뜸 | 210행 / 26레시피 → `g`. 결손 **0** |
| 이름 오염 복구 | 재료 `name`에 `주재료`, `[소스소개] 잣소스` 같은 머리말이 섞여 들어감 | 305레시피 재구성. 오염 **770 → 267행** |
| 그룹 복원 | 원문의 재료 묶음 머리말을 담을 곳이 없어 버려짐 | `ingredient_group` 컬럼 + 952레시피 / 2,957행 / 163종 |

세 작업은 순서가 강제된다 — **이름을 고쳐야 그룹이 드러나고**, 단위 판정 근거가 그대로 파서에 들어간다.

## 핵심 설계 결정 (근거는 워크로그)

- **Flyway가 아니라 `infra/maintenance/` 일회성 스크립트로 운영에 반영했다.** 데이터 교정은 스키마가
  아니고, 재실행 가능해야 할 대상도 아니다. 스키마 변경(`ingredient_group` 컬럼)만 마이그레이션으로 남겼다.
- **이름은 표면 수정이 아니라 원문 재파싱 후 `DELETE` + `INSERT`.** 오염된 문자열을 잘라내는 방식은
  어디까지가 머리말인지 판정할 근거가 행 안에 없다. 대신 **재료 `id`가 결정론적**이라
  (`uuid5(uuid5(URL, '…/recipe-ingredient'), '<recipe_id>:<sort_order>:<name>')`) 재계산이 가능했고,
  계산한 2,957개가 운영에 하나도 빠짐없이 존재해 id 규칙이 실제로 재현된다는 것까지 검증됐다.
- **그룹은 이름 접두어가 아니라 별도 컬럼.** 접두어가 바로 이번 오염의 원인이었다.
- **그룹 값 163종을 정규화하지 않았다.** 정규화는 나중에 언제든 할 수 있지만 합쳐버린 값은 되돌릴 수 없다.
  후보 전체 목록은 `infra/maintenance/tools/ingredient-group-values.txt`에 있다.
- **매칭은 추측하지 않는 두 경로만 썼다.** 재계산으로 id가 확정되는 행, 그리고 파싱 결과가 현재 행과
  `(이름, 수량, 단위)` 순서까지 완전히 일치하는 행. 애매한 것은 손대지 않고 남겼다.

## 스키마 / API 변경

- **스키마**: `V15__add_recipe_ingredient_group.sql` — `recipe_ingredients.ingredient_group TEXT` (NULL 허용)
  + `(recipe_id, ingredient_group)` 인덱스. `ADD COLUMN IF NOT EXISTS`인 이유는, 백필이 배포를 기다릴 수
  없어 운영에는 유지보수 스크립트로 컬럼을 먼저 넣었기 때문이다. 배포 시 운영에서는 무해하게 지나가고
  새 환경에서는 컬럼을 만든다.
- **API 변경 없음.** 엔티티가 이 컬럼을 매핑하지 않으므로(`ddl-auto: validate`는 매핑되지 않은 컬럼을
  문제 삼지 않는다) **응답은 적용 전후 완전히 동일하다.**

## 운영 반영 상태

**세 작업 모두 운영 DB에 반영이 끝났다.** 이 PR은 그 결과를 코드베이스에 남기는 것이고,
새로 실행되는 것은 새 환경에서의 `V15`뿐이다.

반영 절차는 3회 모두 **백업(`manual/`) → 리허설(`ROLLBACK`) → 적용 → 전수 회귀 대조**를 거쳤다.
백업 위치는 워크로그 마지막에 있다.

## 알려진 약점 · 후속

- **`personal_ingredient_adjustments.original_ingredient_id`가 `recipe_ingredients(id)`를
  `ON DELETE CASCADE`로 참조한다.** 재료 행을 지우면 사용자 개인 레시피 수정이 조용히 함께 지워진다.
  이번 `DELETE` + `INSERT`는 그 테이블이 **0행이라 안전했을 뿐**이고, 실사용자가 개인화를 시작하면
  같은 방식을 재사용할 수 없다. 스크립트가 전제조건으로 이를 검사해 거부한다.
- **카탈로그 임포터가 repo에 없다.** 운영 DB가 유일본이다. 이번에 만든 파서
  (`infra/maintenance/tools/`)가 임포터를 다시 쓸 때의 출발점이다.
- 이름 오염 **잔여 267행 / 139레시피** — 원문이 애매해 사람 판단이 필요하다.
  건별 이유를 `infra/maintenance/tools/deferred-recipes.json`에 남겼다.
- 그룹이 비어 있는 **198레시피** — 113개는 원문 애매, 72개는 정렬 불일치.
- **그룹 API·프론트 노출 미작업** — 조리 화면에서 그룹별로 묶으려면 엔티티 필드 + DTO 작업이 따라야 한다.
- **그룹 값 163종 정규화** — 분류 체계를 세울 때. 레시피 태그 작업(#68)과 겹치는 영역이다.
