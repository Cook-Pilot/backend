# 레시피 태그 원문 백필 — 도구

`V14` 가 만든 태그 사전에 **원문의 음식형태·조리법을 옮겨 담기 위한 도구**. 설계 배경은
[`feat-recipe-tags.md`](feat-recipe-tags.md), 제약 보강은
[`fix-recipe-tag-constraints.md`](fix-recipe-tag-constraints.md).

**이 PR 은 도구와 문서만 담는다.** 실제 반영 SQL 은 입력 두 개가 있어야 만들어지는데
(아래 "아직 못 한 것"), 그건 운영 데이터라 어차피 커밋 대상이 아니다.

## 무엇을 왜

지금 `tags` 24행에 `recipe_tags` 0행이다. 사전만 있고 부여가 없어서 태그는 사실상 존재하지 않는다.

부여를 채우는 방법은 두 가지인데 성질이 아주 다르다.

| | 근거 | 커버 |
| --- | --- | --- |
| **원문 백필 (이 도구)** | `RCP_PAT2`·`RCP_WAY2` 를 그대로 옮김. **추론 0** | DISH 1,119 · METHOD 846 |
| LLM 분류 (나중) | 모델 판단 | CUISINE · OCCASION |

원문에 이미 답이 있는 구간을 LLM 으로 채우면 **틀릴 수 있는 것을 공짜로 늘리는 것**이라,
이쪽을 먼저 한다. 문화권·용도는 원문에 아예 없어서 LLM 말고는 길이 없다.

## 판정 규칙

- **매칭은 제목(`RCP_NM`)으로만.** 임포터가 `RCP_SEQ` 를 저장하지 않아 다른 열쇠가 없다.
- **제목이 겹치면 축별로 판단한다.** 그 그룹의 값이 전부 같으면 어느 행에 대응되든 결과가
  같으므로 부여하고, 하나라도 다르면 **그 축만** 건너뛴다. `DISH` 는 확정인데 `METHOD` 만
  갈리는 경우가 있어서 레시피 통째로 버리지 않는다.
- **`기타` 는 미부여.** 사전에 `기타` 태그를 만들지 않았다(만개의레시피 상황축이 커버리지
  95% 인데 57% 가 `일상` 한 값에 몰려 죽어 있는 것이 근거). 미부여는 나중에 채울 수 있지만
  `기타` 로 채운 행은 되돌릴 근거가 없다.
- **사전에 없는 원문 값은 조용히 넘기지 않고 센다.** 원문에 새 분류가 생겼다는 뜻이다.
- `assigned_by = 'IMPORT'`, `confidence` 는 비운다 — 원문 값이지 확신도를 매길 추정이 아니다.

## 담은 것

```
infra/maintenance/tools/
  fetch_recipe_source.py        원문 수집 → source.json
  extract_recipe_tags.py        source + details → tag_assign.json
  gen_recipe_tags_sql.py        tag_assign + details → 반영 SQL
  test_extract_recipe_tags.py   판정 규칙 테스트 (원문·DB 불필요)
  README.md                     파이프라인과 입력 파일 만드는 법
```

생성되는 SQL 은 8/17 데이터 복구와 같은 형태다 — `BEGIN` / `LOCK` / 전제조건 / 적용 / 검증 /
`COMMIT`. 감사 스냅샷과 다르면 일부러 실패한다. 전제조건은 레시피 총수, 대상 id 존재,
사전에 있고 파생이 아닌 태그인지, **배타축이 이미 붙어 있지 않은지**(재실행 방지)를 본다.

## `README.md` 를 같이 넣는 이유

8/17 에 만든 도구들이 `details.json`·`source.json`·`rebuild.json`·`group_assign.json` 을
읽는데, **그게 뭔지 어떻게 만드는지가 어디에도 없었다.** 도구를 커밋해 두고 "임포터를 다시
쓸 때의 출발점" 이라고 적어놨지만 남이 실행할 수가 없는 상태였다. 이번에 파이프라인 전체와
각 입력을 만드는 SQL·명령을 적었다.

## 검증

`python3 test_extract_recipe_tags.py` — 17개 확인, 전부 통과. 원문도 DB 도 필요 없다.

제목 중복 시 축별 판단, `기타` 미부여, `국&찌개`(원문은 `&`, 태그 라벨은 `·` 라 헷갈리기 쉽다),
미매칭, 사전에 없는 값, 제목 앞뒤 공백을 본다.

파이프라인 전체는 샘플 5행으로 끝까지 돌려 SQL 생성까지 확인했다.

## 아직 못 한 것 — 입력 두 개가 없다

1. **원문 전량.** **`sample` 키로는 안 된다** — 2026-08-19 확인 기준 요청 구간과 무관하게 늘
   같은 5행(`RCP_SEQ` 28·29·31·32·33)만 온다. `total_count` 는 1156 으로 정상 보고해서
   행 수를 세지 않으면 조용히 5건짜리 결과가 나온다(`fetch_recipe_source.py` 가 이걸 검사한다).
   공공데이터포털 발급 키가 필요하다.
2. **운영 DB 덤프**(`details.json`). SSM 접근이 필요하다.

둘이 준비되면 `extract → gen` 두 번으로 반영 SQL 이 나온다.

## 순서

**`V17`(PR #75) 이 먼저 머지돼야 한다.** `recipe_tags` 가 비어 있을 때 제약을 걸어야 싸고,
백필하고 나면 약 2,000행을 놓고 제약을 추가하게 된다. 백필 SQL 자체는 V17 이전에도 돌지만
(전제조건이 `match_rule IS NULL` 로 검사한다) 순서를 바꿀 이유가 없다.

백필 다음은 `GET /recipes` 의 `tags=` 파라미터, 그리고 `web/lib/gemini.ts` 의 자유 문자열
태그를 사전 code 로 교체하는 일이다 — **사전의 첫 소비자는 앱이 아니라 Gemini 다.**
