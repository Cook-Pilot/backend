## 배경

2026-08-04 회의에서 룰베이스 확장 방향에 제동이 걸렸다. 회의록 4번 항목의 표현을 그대로 옮기면:

> 룰베이스로 다 커버 가능? → 안됨 → 싹다 API 던져잇!
> 일단 llm 다 던지기로 구현하고 수정해나가야 함. 지금 너무 밀림.
> 차이점을 줘야하는 부분은 룰베이스가 아니라 RAG, 맛 벡터, 버전 추적 이런 걸로 해야 함.

동시에 지금 코드에 박혀 있던 전제 하나를 검증 대상으로 명시했다.

> 알레르기 같은 건 위험하니까 llm 던지지 말자~ → **실제로 llm이 대답 잘 못함?**

단, 단발성 로컬 명령(타이머 연장, 다음 단계)은 룰베이스 유지가 낫다는 단서가 함께 달렸다. 이 부분은
프론트 `CommandRouter` 소관이라 이번 백엔드 변경 범위 밖이다.

## 결정

**판단이 필요한 질문은 안전 질문을 포함해 전부 Gemini로 보낸다.** 룰베이스는 삭제하지 않는다.

`CoachService`의 경로는 이렇게 바뀌었다.

| | 이전 | 이후 |
|---|---|---|
| 안전 질문 | 룰베이스가 LLM 앞에서 가로챔 (항상) | 기본적으로 LLM으로 감. 플래그로 가로채기 복원 가능 |
| 일반 조리 질문 | LLM | LLM (동일) |
| LLM 실패·미설정 | 룰베이스 fallback | 룰베이스 fallback (동일, 안전 규칙 먼저 확인) |

## 룰베이스를 남긴 방식

삭제하지 않고 두 자리에 남겼다.

1. **LLM 앞 안전 인터셉트** — `cookpilot.ai.safety-intercept-enabled` (기본 `false`).
   환경변수 `COOKPILOT_SAFETY_INTERCEPT=true`로 즉시 이전 동작으로 되돌아간다.
2. **LLM 뒤 fallback** — 플래그와 무관하게 항상 동작한다. Gemini가 죽었을 때 답할 무언가는
   LLM 의존도가 높아질수록 오히려 더 필요하다.

검토했으나 기각한 보존 방식:

- **코드를 지우고 git 이력에만 의존** — 기각. 되살리려면 커밋을 찾아 되돌려야 해서 비교 실험이 번거롭다.
  회의가 요구한 것은 "LLM이 실제로 대답을 잘 못하는지" 확인이고, 그러려면 두 동작을 번갈아 켤 수 있어야 한다.
- **`legacy/` 디렉터리로 복사** — 기각. 컴파일은 되지만 호출되지 않는 죽은 코드가 되어 테스트가 썩는다.
- **별도 브랜치에만 보존** — 기각. 위와 같은 이유이고, main 계열에서 실험을 못 한다.

되돌릴 기준점으로 태그 `rulebase-coach-v1`을 커밋 `e32ea68`에 달아 두었다.

## 함께 바꾼 것

**Gemini 프롬프트에 안전 지침을 구체화했다.** 안전 질문의 1차 응답자가 룰베이스에서 LLM으로 넘어갔으므로,
룰베이스가 갖고 있던 내용을 프롬프트로 옮겼다. 특히 기름불에 물을 붓지 말라는 지시는 틀리면 사람이 다치는
항목이라 명시했다. 변질·알레르기·덜 익은 육류도 각각 구체적 행동으로 적었고, 판단이 서지 않으면 조리를
계속하라고 하지 말라는 지시를 더했다.

**`ai_interactions.model`에 경로를 구분해 기록한다.** 이전에는 룰베이스가 답한 모든 경우가
`local-safety-rules` 하나로 뭉뚱그려져, 안전 인터셉트가 답한 것인지 Gemini가 죽어서 fallback이 답한 것인지
사후에 구분할 수 없었다. 네 경로를 분리했다.

| 라벨 | 의미 |
|---|---|
| `local-safety-intercept` | 플래그가 켜져 룰베이스가 LLM 앞에서 가로챔 |
| (모델명, 예: `gemini-2.5-flash`) | LLM이 답함 |
| `local-safety-fallback` | LLM 실패 후 룰베이스 안전 규칙이 답함 |
| `local-rule-fallback` | LLM 실패 후 일반 fallback이 답함 |

이 구분이 있어야 회의가 요구한 비교 측정이 가능하다.

## 검증

- `CoachServiceTest` 5개 — 네 경로의 분기와 라벨 기록을 각각 확인한다.
- `CoachServiceConfigBindingTest` 1개 — 프로퍼티가 실제 Spring 컨텍스트에서 바인딩되는지 확인한다.
  유닛 테스트는 생성자를 직접 호출하므로 키 이름이 틀려도 통과한다. 키를 잘못 적으면 조용히 기본값으로
  떨어져 스위치가 죽으므로 컨텍스트를 띄워 따로 검증한다. 키를 일부러 틀리게 바꿔 이 테스트가 실패하는 것까지
  확인했다.
- 백엔드 전체 38개 통과.

## 남은 위험과 해야 할 일

**이 변경의 핵심 위험은 안전 질문의 답을 결정론적 규칙에서 확률적 모델로 넘겼다는 것이다.**
"기름에 불이 붙었어"에 대해 룰베이스는 항상 같은 답을 했지만 이제는 모델 응답에 달려 있다. 프롬프트로
방어했으나 프롬프트는 보장이 아니다. 다음이 실측 전에 실서비스로 나가면 안 되는 이유다.

1. **안전 질문 실측** — 회의가 요구한 항목. 변질/알레르기/덜 익은 육류/기름불 각 카테고리에 고정
   말뭉치를 만들고 `safety-intercept-enabled` on/off로 응답을 비교한다. LLM 응답이 보수적 기준을
   만족하지 못하면 기본값을 `true`로 되돌린다.
2. **Gemini 실패 관측성** — `GeminiCoach`가 아직 모든 예외를 삼킨다(`catch (Exception) → empty()`).
   실측 중 fallback으로 떨어져도 타임아웃인지 4xx인지 파싱 실패인지 알 수 없다. 1번의 전제 조건이다.
3. LLM 호출 비중이 올라가므로 이전에 남긴 두 건의 우선순위도 함께 올라간다 — `/ai/feedback`의
   `Idempotency-Key` 부재(재시도 시 중복 과금), 서버측 호출 가드 부재.
