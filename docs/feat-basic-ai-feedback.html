조리 중 AI 피드백에 Spring AI 붙이기

POST /api/v1/ai-feedback 이 고정 목데이터 대신 실제 LLM 을 호출한다. 그리고 응답 계약을 실제로 쓰는 것만 남기고 잘라냈다 — 남은 건 {mock, speechText} 둘. 설계의 실질은 “LLM 이 없거나 느리거나 이상해도 불 앞에 선 사용자는 답을 듣는다”를 구조로 보장한 것이다.

./gradlew build 통과 Spring AI 2.0.0 google-genai 마이그레이션 0건 호출 타임아웃 10s 응답 필드 3개 제거 기본값 = 목 응답

01 요청 하나가 지나는 세 개의 관문

LLM 경로는 조건부다. 세 관문 중 하나라도 걸리면 응답은 조용히 목 문장으로 떨어진다 (mock: true). 실패가 사용자에게 500 으로 새어 나가는 경로는 없다.

GATE 3 이 한 칸으로 줄어든 것이 이번 작업의 결론이다 — 자세한 건 04.

02 버전은 고를 수 있는 게 아니었다

이 저장소는 Spring Boot 4.1.0 · Jackson 3(tools.jackson) 라인이다. Spring AI 1.1.x 는 Boot 3 · Jackson 2 전용이라 올리면 자동설정부터 깨진다. 2.0.0 의 spring-ai-starter-model-google-genai pom 에는 spring-boot 4.1.0 이 그대로 박혀 있다 — 우리와 같은 라인이다.

 Spring AI 1.1.xSpring AI 2.0.0이 저장소
대상 Boot3.x4.1.04.1.0
Jackson2 · com.fasterxml3 · tools.jackson3 · tools.jackson
결과기동 불가정합—

Boot BOM 은 spring-ai 버전을 관리하지 않는다. springdoc · testcontainers 와 같은 상황이라 platform('org.springframework.ai:spring-ai-bom:2.0.0') 을 따로 가져온다.

“API 키만 바꾸면 모델 교체 자유” — 절반만 맞다

  • 같은 프로바이더 내 모델 교체 (gemini-3.5-flash → pro): AI_CHAT_MODEL env 하나. 재빌드 없음.
  • 프로바이더 교체 (Gemini → OpenAI/Claude): 스타터 의존성 교체 + 재빌드 필요. 프로퍼티 prefix 도 키도 다르다.
  • 그래도 남는 실익: 호출 코드(ChatClient)는 그대로다. F-11 처럼 벤더 와이어 DTO 를 손으로 짰다면 통째로 다시 썼어야 한다.

03 조용히 무너지는 세 지점

앞의 둘은 “빈이 없으면 조용히 없겠지”라는 가정이 틀려 기동을 죽였다. 셋째는 아무것도 죽이지 않고 운영에서만 드러난다.

함정 1 · 자동설정이 기본으로 켜진다

키가 없으면 앱이 뜨지 않는다

GoogleGenAiChatAutoConfiguration 의 조건은 @ConditionalOnProperty(name="spring.ai.model.chat", havingValue="google-genai", matchIfMissing=true). 값을 안 주면 켜지고, 키가 없으면 빈 생성에서 죽는다. 

Incomplete Google GenAI configuration: Provide 'api-key' for
Gemini API or 'project-id' and 'location' for Vertex AI.

대응 — CI · 로컬 · 모든 테스트에 키가 없다. application.yml 기본값을 ${AI_CHAT_PROVIDER:none} 로 못 박고, 켤 때만 google-genai 를 넣는다.

함정 2 · 빈 정의는 있고 의존성은 없다

ObjectProvider<ChatClient.Builder> 가 null 을 안 준다

ChatClientAutoConfiguration 은 ChatModel 유무와 무관하게 chatClientBuilder 빈 정의를 등록한다. 그래서 모델이 없을 때 getIfAvailable() 이 null 대신 예외를 던진다. 

Error creating bean 'chatClientBuilder' ... :
No qualifying bean of type
'org.springframework.ai.chat.model.ChatModel' available

대응 — ObjectProvider<ChatModel> 로 받는다. provider 가 none 이면 정의 자체가 없어 깨끗하게 null 이 나온다. ChatClient 는 ChatClient.builder(model) 로 직접 만든다.

함정 3 · SDK 기본값이 무한대

타임아웃을 아무도 걸어 주지 않는다

google-genai SDK 는 타임아웃을 명시적으로 끄고 시작하고, Spring AI 의 spring.ai.google.genai.* 에는 타임아웃 프로퍼티가 아예 없다 (설정 메타데이터 전수 확인). Gemini 가 응답하지 않으면 서블릿 스레드가 영구 점유돼 톰캣 스레드풀이 마른다. 

// google-genai 1.58.0 ApiClient.java
// Remove timeouts by default (OkHttp has a default of 10 seconds)
builder.connectTimeout(Duration.ofMillis(0));
builder.readTimeout(Duration.ofMillis(0));
builder.writeTimeout(Duration.ofMillis(0));
httpOptions.timeout().ifPresent(t -> builder.callTimeout(...));  // 안 주면 무한

대응 — Spring AI 의 googleGenAiClient 빈이 @ConditionalOnMissingBean 이라, GoogleGenAiClientConfig 에서 같은 타입을 먼저 등록해 자동설정을 물러나게 하고 HttpOptions.timeout(10_000) 을 건다. 초과 예외는 GenAiIOException(→ RuntimeException)이라 기존 catch 가 그대로 잡아 목 응답으로 흡수한다.

함정 3 은 실패해도 조용하다 — 우리 빈이 자동설정에 밀리면 타임아웃만 사라지고 호출은 계속 된다. 그래서 AiFeedbackWiringTest 가 “이 Client 를 누가 만들었는가”를 빈 정의로 직접 단언한다.

함정 1·2 는 평소 실행에서 절대 밟히지 않는다(기본값이 none 이므로). 배포 직전까지 모를 구멍이라 AiFeedbackWiringTest 가 더미 키로 “AI 를 켠 컨텍스트가 뜨는지”를 지킨다.

04 구조화 출력을 짓고, 다시 버렸다

처음에는 CookingAdvice 레코드로 구조화 출력을 받았다 — speechText · screenText · actionType · seconds · problem · adjustment. 옛 MVP 문서의 LLM 응답 구조를 그대로 옮긴 것이었고, AiFeedbackResponse 도 main 부터 같은 모양이었다.

스키마가 모양은 강제해도 값 조합은 강제하지 못해서, 검증 코드 (normalize() 21줄 + 상수 3개 + 테스트 5개)를 따로 얹어야 했다. 그러다 필드 하나하나에 “지금 이걸 누가 쓰나”를 물었더니 답이 없었다.

뺀 필드이유
suggestedAction{type, seconds} 프론트가 앞단에서 처리하기로 했다. 서버가 행동 어휘를 정의하면 그게 곧 클라이언트 계약이 되는데, 지금 그럴 근거가 없다
eventPayload{problem, adjustment} 분석용 영문 라벨. 서버도 저장하지 않고 프론트에도 소비 코드가 없다 — 순수 데드웨이트였다
screenText 화면 표시 문구도 프론트가 정한다

남은 것은 {mock, speechText} 둘. 필드가 하나면 구조화 출력을 쓸 이유가 없어 …entity(CookingAdvice.class) 를 .content() 로 바꿨고, 검증 코드가 통째로 사라졌다.

남은 검증은 “빈 문자열이면 버린다” 하나뿐이다. 형식은 프롬프트에 맡긴다 — 읽히는 것이 문장 하나뿐이라 모델이 형식을 어겨도 폭발 반경이 없다. 필요해지면 그때 필드를 늘린다. 늘리는 쪽이 줄이는 쪽보다 싸다.

프롬프트에 못 박은 세 가지

  • 안전 원칙 4줄 — 변질 의심 단정 금지 · 덜 익은 육류는 추가 가열 우선 · 알레르기는 보수적 · 화기 위험 최우선. 모델 재량에 맡기지 않는다.
  • 되묻기 금지 — 입력은 STT 결과라 오인식 · 잡음 · 끊긴 문장이 섞인다. 조리 중에 되묻는 것은 사용자에게 가장 비싼 응답이다.
  • 머리말 · 목록 · 마크다운 금지 — 응답이 그대로 TTS 로 읽힌다.

05 계약 — 바뀐 것과 바뀌지 않은 것

바뀌지 않음

  • 요청 {recipeId, stepIndex, userSpeech} — userSpeech 는 여전히 클라이언트가 STT 로 변환해 보낸 문자열이다. 서버는 음성을 받지 않는다. 오디오를 서버가 직접 받게 되면 이 요청은 JSON 이 아니라 multipart 가 되고 경로 전체가 바뀐다.
  • DB — 마이그레이션 0건. AI 피드백은 아무것도 저장하지 않는다.
  • 무상태 — 조리 세션 · 타이머 · 이벤트 로그는 계속 프론트가 들고 있다.

바뀜 — 응답 필드 제거 (파괴적)

// before
{ "mock": true, "speechText": "...", "screenText": "...",
  "suggestedAction": { "type": "EXTEND_TIMER", "seconds": 60 },
  "eventPayload": { "problem": "...", "note": "...",
                    "currentStepIndex": 0, "userSpeech": "..." } }

// after
{ "mock": false, "speechText": "..." }

mock 의 뜻도 바뀌었다. 예전엔 “AI 파트 미확정”, 지금은 “이번 응답이 LLM 이 아니라 목데이터인가”. 프론트가 이걸 개발중 배지로 쓰고 있었다면 다시 읽어야 한다.

docs/openapi.json 재생성 완료(SuggestedAction 스키마 제거). CI 가 코드와 스냅샷 일치를 검사하므로 이 파일이 밀리면 파이프라인이 막힌다.

07 알려진 약점 · 후속

  1. 실제 호출 경로는 자동 테스트가 없다. AiFeedbackWiringTest 는 더미 키로 배선만 본다. 프롬프트가 쓸 만한 답을 내는지는 키를 꽂고 수동으로 확인해야 한다.
  2. 응답 형식 보장이 프롬프트뿐이다. 모델이 머리말이나 목록을 붙이면 그대로 TTS 로 읽힌다. 구조화 출력을 버린 대가다 — 실제로 얼마나 자주 어기는지는 운영에서 봐야 한다.
  3. AI 호출 경로가 2개다. F-11 은 손코딩 RestClient(GeminiRecommendationExplanationClient), 이번 건은 Spring AI. 설정도 cookpilot.ai.gemini.* 와 spring.ai.* 로 이원화돼 있다. 의도적으로 이번 범위에서 뺐다 — 이관은 별도 PR.
  4. userSpeech 길이 상한이 없다. 무인증 엔드포인트라 큰 텍스트를 계속 밀어 넣으면 쿼터를 태울 수 있다. 프론트가 STT 결과 길이를 제한하는 전제로 이번 범위에서 뺐다 — 서버로 넘어오면 컨트롤러에 상한을 건다.
  5. 비용 · 쿼터 제어가 없다. 레이트리밋도 캐시도 없다. 무료 티어를 넘기면 매 호출이 실패해 전부 목으로 떨어진다 — 사용자에게는 조용히. 베타 규모에서는 감수, 이후 관측 지표가 필요하다.
  6. 조리 상태를 안 넘긴다. 타이머 잔여시간 · 최근 이벤트가 프롬프트에 없다. “3분 중 20초 남음”을 모르는 상태로 조언하는 셈이다. 요청 DTO 확장이 선행돼야 한다.
