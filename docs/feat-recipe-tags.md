# 레시피 분류 태그 — 스키마와 사전

`V14__add_recipe_tags.sql` 로 들어간 태그 구조의 설계 기록. PR #68 때 이 문서를 빠뜨려서
뒤늦게 채운다(제약 보강 브랜치 `fix/recipe-tag-constraints` 에서 함께 작성).
V14 이후의 변경은 [`fix-recipe-tag-constraints.md`](fix-recipe-tag-constraints.md) 에 있다.

## 무엇을 왜

문화권·음식형태·조리법·용도를 한 구조로 담는다. 자유 문자열 배열(JSONB)로 두지 않은 이유는
**이미 오염이 실측됐기 때문**이다 — 웹 시드 8건에 태그 14종인데 `볶음밥`/`볶음요리` 가 갈리고
`한그릇`/`초간단`/`15분요리` 가 같은 뜻으로 셋이다. 유튜브 추출(`web/lib/gemini.ts`)이 자유
문자열 태그를 계속 만들어내므로 사전에서 고르게 하지 않으면 오염이 누적된다.
같은 문제를 `recipe_ingredients.ingredient_group` 에서 이미 한 번 겪었다.

## 구조

레시피와 태그의 M:N 을 연결 테이블로 푼 표준 형태다. 다만 **교과서 형태에서 두 군데 일부러
벗어나 있어서**, 그 근거를 아래에 남긴다.

```
tags          code(PK) · axis_code · label_ko · sort_order · is_active · match_rule
recipe_tags   recipe_id · tag_code · axis_code · assigned_by · confidence
              · model · prompt_version · assigned_at
```

### `axis_code` — 태그가 답하는 질문의 종류

| 축 | 질문 | 배타성 | 시드 |
| --- | --- | --- | --- |
| `CUISINE` | 어느 나라 음식인가 | 배타 | 한식·일식·중식·양식·아시안·퓨전 |
| `DISH` | 어떤 형태의 음식인가 | 배타 | 반찬·일품·후식·밥·국찌개 |
| `METHOD` | 어떻게 조리하는가 | 배타 | 끓이기·굽기·볶기·찌기·튀기기 |
| `OCCASION` | 언제·무슨 용도인가 | 다중 | 안주·도시락·손님상·아이반찬·다이어트·초스피드·야식·명절 |

**축은 앱에 내려보내지 않는다.** 화면에는 `한식 · 밥 · 볶기 · 초스피드` 가 전부 같은 모양의
칩 한 줄로 나가고 사용자는 축이 있는 줄 모른다. 축은 두 가지에만 쓴다.

1. **배타성 강제** — 한식이면서 일식일 수 없다. 부분 유니크 인덱스가 `CUISINE`·`DISH`·`METHOD`
   에만 걸리고 `OCCASION` 은 빠진 이유다(안주이면서 야식인 것은 정상).
2. **필터 의미** — 축 안은 OR, 축 사이는 AND. `?tags=DISH_SIDE,DISH_RICE,OCCASION_KIDS`
   는 (반찬 or 밥) and 아이반찬이다. 축을 모르면 이 조합 규칙을 만들 수 없다.

만개의레시피는 문화권 축이 없어서 `양식`·`퓨전` 이 요리종류 축에 침범해 있다.

## 벗어난 곳 ① — 대리키를 두지 않았다

설계 초안은 `tags(id PK, code UNIQUE, …)` 였다. 구현에서 **`code` 자체를 PK** 로 바꿨다.

- `code` 는 API 파라미터(`?tags=CUISINE_KOREAN`)로 그대로 나간다. **어차피 안정적이어야 하는
  값**이라, 대리키가 주는 "코드를 자유롭게 개명할 수 있다"는 이점이 실현되지 않는다.
- 대리키를 두면 `recipe_tags` 를 눈으로 읽을 수 없다. `(uuid, 47)` 보다 `(uuid, 'DISH_SIDE')` 다.
- URL 에 뜻이 남으면 공유·딥링크·SEO 에 쓸모가 있다. 우리의식탁은 태그를 URL 에 남기지 않아
  그것을 통째로 포기했다.

**대리키로 갔어도 틀린 설계가 아니다.** 다만 그 경우 URL 에 박히는 값이 뜻 없는 숫자가 되고,
얼어붙는 대상이 `code` 에서 `id` 로 옮겨갈 뿐이다 — **밖으로 내보낸 것은 무엇이든 얼어붙는다.**
어느 쪽을 얼릴지의 선택이었고, 읽히는 URL 쪽을 택했다.

바뀔 수 있는 것은 열쇠에서 분리했다. `label_ko`("반찬" → "밑반찬")는 PK 가 아니라 언제든 고친다.

자연키의 통상적 단점(개명하면 참조가 깨진다)은 **V17 의 `ON UPDATE CASCADE` 로 해소**했다.
V14 에는 그게 빠져 있어서 자연키를 쓰면서 완화 장치는 없는 상태였다.

## 벗어난 곳 ② — `axis_code` 를 중복 저장한다 (2NF 위반)

`recipe_tags` 의 후보키는 `(recipe_id, tag_code)` 인데, `tag_code → axis_code` 라는 함수 종속이
있다. 즉 비주요 속성이 후보키의 **진부분집합에만** 의존한다 — **부분 함수 종속이라 2NF 위반**이고
3NF·BCNF 도 함께 깨진다.

그럼에도 중복 저장하는 이유는 배타성 인덱스 때문이다.

```sql
CREATE UNIQUE INDEX uq_recipe_tags_exclusive_axis
  ON recipe_tags(recipe_id, axis_code)
  WHERE axis_code IN ('CUISINE', 'DISH', 'METHOD');
```

**부분 인덱스는 다른 테이블의 컬럼을 참조할 수 없다.** 배타성을 애플리케이션이 아니라 DB 가
강제하려면 `axis_code` 가 물리적으로 `recipe_tags` 안에 있어야 한다.

정규화가 막아주는 것은 **갱신 이상**(사전의 축을 바꿨는데 사본이 옛 값으로 남는 것)이고,
그건 복합 FK 로 대신 막는다.

```sql
-- tags 쪽:        UNIQUE (code, axis_code)     ← code 가 이미 PK 라 논리적으로 잉여.
--                                                 오직 아래 FK 의 대상이 되기 위해 존재한다.
-- recipe_tags 쪽: FOREIGN KEY (tag_code, axis_code) REFERENCES tags(code, axis_code)
```

**정규형을 깨되 깨진 만큼을 제약으로 되사오는** 교환이다. 축을 늘릴 때는 `tags.axis_code` 의
CHECK 와 위 부분 인덱스 두 곳을 함께 고쳐야 한다(부분 인덱스가 다른 테이블을 못 보므로
축 목록이 두 곳에 있다).

## 연결 테이블이 id 두 개가 아닌 이유

`assigned_by` / `confidence` / `model` / `prompt_version` / `assigned_at` 은 레시피의 속성도
태그의 속성도 아니고 **"이 레시피에 이 태그가 붙었다는 사실"의 속성**이다.

부여 출처를 행마다 남기지 않으면 분류기 v2 배치가 사람 검수를 조용히 덮어쓴다(재료 행 삭제가
개인화 diff 를 CASCADE 로 지우는 것과 같은 종류의 사고다). LLM 이 붙인 것은 어느 모델·어느
프롬프트였는지 없으면 재현도 롤백도 못 해서, `assigned_by='LLM'` 이면 `model`·`prompt_version`
을 필수로 거는 CHECK 가 있다.

## 사전에 담은 것과 담지 않은 것

- **음식형태·조리법은 원문 값 그대로다.** 식품안전나라 `COOKRCP01` 의 `RCP_PAT2` / `RCP_WAY2`.
  결손이 0 이라 추론 없이 1,150 건을 채울 수 있지만, **그 백필은 이 마이그레이션에 없다** —
  원문과 DB 를 제목(`RCP_NM`)으로 조인해야 하고(`RCP_SEQ` 미저장) 제목 중복이 13 그룹 있어서,
  스키마가 아니라 유지보수 스크립트로 다룰 일이다.
- **`기타` 는 태그로 만들지 않았다**(원문 요리종류 37건, 조리방법 310건). 만개의레시피 상황축이
  커버리지 95% 인데 그 중 57% 가 `일상` 한 값에 몰려 필터로서 죽어 있다. 고르기 애매할 때
  도망갈 칸을 주면 축이 무의미해진다. **애매하면 미부여** — 미부여는 나중에 채울 수 있지만
  `기타` 로 채운 행은 되돌릴 근거가 없다.
- **용도 8개는 확정이 아니라 후보다.** 분류를 돌린 뒤 건수가 적은 태그는 `is_active=false` 로
  내린다. 1,150 건에서 태그 하나가 한 화면(약 20건)도 못 채우면 눌렀을 때 앱이 비어 보인다.
- **문화권 축은 지금 값을 하지 않는다.** 카탈로그가 사실상 전량 한식이고, 유튜브 레시피가
  들어와야 쓸모가 생긴다. 그래도 지금 만들어 두는 이유는 축이 없으면 `양식` 이 음식형태 축에
  끼어들어 배타성을 깨뜨리기 때문이다.
