# feat/recipe-tag-filter — 태그로 레시피 거르기

## 무엇을 왜

부여(V21)가 채워져도 **태그로 거르는 길이 없으면 홈 화면은 그대로다.** 넷플릭스식 개편
(Cook-Pilot/frontend#63)이 상단 카테고리 칩을 못 넣은 이유가 이것이다. 이 PR 이 그 관문을 연다.

## 규칙 — 축 안은 OR, 축 사이는 AND

V14 가 정한 의미 그대로다.

```
?tags=METHOD_GRILL&tags=METHOD_BOIL&tags=DISH_SIDE
  → (굽기 OR 끓이기) AND 반찬
```

**클라이언트는 축을 몰라도 된다.** 요청한 코드가 걸친 축의 수를 서버가 세고, 레시피가 그만큼의
축을 만족하는지 본다.

```sql
:tagAxisCount = (SELECT COUNT(DISTINCT axis_code) FROM recipe_tags
                  WHERE recipe_id = recipe.id AND tag_code IN :tagCodes)
```

축 정보를 응답에 넣지 않은 것도 같은 이유다 — 내려보내면 이 규칙이 클라이언트에도 심긴다.
V14 도 "화면에는 '한식 · 반찬 · 안주'가 전부 같은 모양의 칩 한 줄"이라고 적어 뒀다.

## 없는 코드는 400

조용히 무시하면 **오타 하나가 "필터가 안 걸린 전체 목록"** 이 되고 클라이언트는 성공으로 읽는다.
태그 코드는 URL 에 그대로 나가는 값이라 오타가 실제로 생긴다(V14 가 `code` 를 PK 로 둔 이유이기도 하다).

## 어디에 붙였나

**기존 `GET /recipes/search` 에 `tags` 를 더했다.** 새 엔드포인트를 만들지 않은 이유는 홈의
카테고리 열이 결국 "이 태그의 레시피를 N개" 라서 페이지네이션이 그대로 필요하고, 검색창과
카테고리를 함께 쓰는 화면(재료 + 태그)이 자연스럽기 때문이다.

`GET /tags` 를 새로 열었다. 칩이 읽을 사전이다.

- **로그인이 필요 없다.** 사전은 개인 데이터가 아니고, 게스트도 카테고리를 눌러 볼 수 있어야 한다(#76 과 같은 이유).
- **비활성 태그는 내리지 않는다.** 분류를 돌린 뒤 건수가 적어 내린 태그가 칩으로 남아 있으면 눌렀을 때 한 화면도 못 채운다 — V14 가 미리 적어 둔 실패 방식이다.

## 엔티티를 두 개 새로 만들었다

`tags`·`recipe_tags` 는 지금까지 엔티티가 없었다(스키마와 사전만 들어간 단계라 테스트가
JdbcTemplate 으로 직접 봤다). 필터 질의와 사전 조회가 둘 다 필요해서 만든다.

`RecipeTagEntity` 는 **부여 출처(assigned_by)·신뢰도·모델을 매핑하지 않았다.** 앱이 아직 태그를
쓰거나 지우지 않아 읽을 일이 없고, JPA 는 매핑한 열만 검증하므로(`ddl-auto: validate`)
필요해질 때 더하면 된다.

## 검증

- 전체 **208개 통과** (신규 8개)
- 축 규칙을 세 갈래로 덮었다: 같은 축 둘(OR), 다른 축 둘(AND), 섞인 경우
- 태그 없음·재료와의 조합·오타 400·사전 조회·게스트 접근

## 이후 작업

- **문화권·용도 부여가 아직 없다.** V21 이 채운 것은 음식형태·조리법뿐이라, 지금 칩을 만들면
  `한식`·`안주` 는 눌러도 비어 있다. LLM 분류가 선행돼야 한다.
- 태그 조합이 흔해지면 `recipe_tags(tag_code, recipe_id)` 인덱스를 볼 것. 지금은 PK 가
  `(recipe_id, tag_code)` 라 태그로 먼저 좁히는 방향의 인덱스가 없다. 1,150행에서는 문제가 아니다.
